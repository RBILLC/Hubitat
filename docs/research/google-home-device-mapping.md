# Why MoonHalo Is Dropped by Google Home, and How to Fix It

Research date: 2026-09-04. Convention: **[DOC]** = stated in official Hubitat or Google documentation (authoritative). **[FORUM]** = a community forum report — an anecdote, not a spec. **[STAFF]** = a post from a Hubitat staff account on the forum (still an anecdote about one case, not published documentation). **[INFERENCE]** = my own reasoning from the above, not stated anywhere in the sources.

---

## One-paragraph answer

Hubitat's own Google Home app performs a pre-flight validation pass on every device it is asked to share, before that device is ever handed to Google's SYNC; a device that fails this pass is silently pulled back out of the "devices to authorize" list and the hub log records "The following devices are not supported by Google Home and will be removed from your device list" [FORUM, evidenced first-hand in the Generic-Zigbee-RGBW thread below] — which matches the MoonHalo symptom (present at authorization, absent from the confirmation screen) exactly. Every forum case with this signature that was actually solved was solved by cutting the device's declared capability/attribute surface down to something the built-in integration recognizes cleanly, not by changing values already reported (MoonHalo's `colorTemperature`, `colorName`, `colorMode` and `switch` were all already non-null at authorization time, so simple "unpopulated attribute" is not the direct cause here). The most likely proximate cause, ranked from the evidence, is that MoonHalo's capability set carries declarations the built-in integration does not expect on a plain CT bulb — `Light` (rather than the `Bulb` capability every official CT-only example driver actually uses), `Initialize`, `Refresh`, and a custom, non-capability `connectionState` attribute and `setColorTempStep` command — any one of which is consistent with the community's repeated, if unverified-by-Hubitat, warning that "Hubitat can use a driver with attributes the device does not actually support — adding that device to Google Home will likely fail" [FORUM]. The first thing to try is free and reversible: say "Hey Google, sync my devices," because Google's own device cache is a documented separate failure mode in one thread; the second is to swap `capability "Light"` for `capability "Bulb"` in the Driver, matching the capability every real CT-bulb example in this repo's own driver-conventions research (`advancedZigbeeCTbulb.groovy`) actually declares.

## 1. What Hubitat documents

Source: https://docs2.hubitat.com/en/apps/google-home (rendered via Chrome, since a plain fetch/curl returns only the page `<title>` — confirmed again on this pass; the page is a client-rendered app). **[DOC]**

Read in full on this pass. Verbatim, the only statement about supported device types: *"Google Home supports switches, dimmers, thermostats, RGB, RGBW and ColorTemperature bulbs."* — the word used is **"bulbs,"** not "lights."

The rest of the page is exclusively a pairing/authorization walkthrough (Google Home app → `+` → Set up device → Works with Google → search Hubitat → sign in with hub admin credentials → choose hub → select devices → Authorize → assign to a room) and the reverse-editing flow inside the hub's own Google Home app (Apps → Google Home → *Which Devices?* checklist → Update → Done). **There is no troubleshooting section on this page at all** — no "device not showing," no "sync," no error-code list, and **no statement of which capabilities or attributes the integration inspects** to decide device type or to accept/reject a device. Everything about *why* a device gets excluded had to come from the community, not Hubitat's docs.

## 2. What Google requires for a light with colour temperature

Note up front: **two different Google APIs were in scope for this research, and only one applies to Hubitat.** Hubitat's "Google Home" app is a **cloud-to-cloud (Smart Home Actions) integration** — Hubitat's own cloud service authenticates to Google and answers SYNC/QUERY/EXECUTE intents on the driver's behalf. The page the user found, `https://developers.home.google.com/apis/android/supported-device-types`, was fetched and confirmed **[DOC]** to describe a *different* surface: the Android **Local Home SDK / Matter local-fulfillment** device-type table (its device type IDs are literally `home.matter.0000.types.010c` etc., and its required traits are Matter cluster traits — `matter Identify`, `matter OnOff`, `matter LevelControl`, `matter ColorControl` — not `action.devices.traits.*`). This page is not the contract Hubitat's cloud-to-cloud app has to satisfy; it's flagged here because the user cited it, but it should not be used to reason about MoonHalo.

The actually-relevant cloud-to-cloud docs, read in full via rendered browser:

- **Light guide** — https://developers.home.google.com/cloud-to-cloud/guides/light **[DOC]**
  - Device type `action.devices.types.LIGHT`.
  - **Required trait: `action.devices.traits.OnOff` only.** ("These traits and commands are required, if applicable to your device.")
  - **Recommended traits: `ColorSetting`, `Brightness`.** Recommended, not required — a bare on/off light is still a valid `LIGHT` device.
  - If a device doesn't support a recommended/required trait's command, the service should answer with `functionNotSupported`, not omit the device.

- **ColorSetting trait** — https://developers.home.google.com/cloud-to-cloud/traits/colorsetting **[DOC]**
  - SYNC attributes: the device must report **at least one** of `colorModel: "rgb"|"hsv"` **or** a `colorTemperatureRange` object. `colorTemperatureRange` itself has two **required** integer fields: `temperatureMinK` and `temperatureMaxK`. A CT-only device (MoonHalo) would report only the `colorTemperatureRange` form.
  - QUERY state: a `color` object containing exactly one of `temperatureK` (Integer), `spectrumRgb`, or `spectrumHsv` — for CT, `{"color": {"temperatureK": <int>}}`.
  - Naming footgun documented explicitly: EXECUTE command params use `spectrumRGB`/`spectrumHSV` (capital RGB/HSV) while QUERY/Report-State use `spectrumRgb`/`spectrumHsv` — camelCase. Not relevant to a CT-only device, but noted since it's the one "gotcha" the trait page calls out.

- **Brightness trait** — https://developers.home.google.com/cloud-to-cloud/traits/brightness **[DOC]**
  - No required SYNC attributes.
  - QUERY state: `brightness`, Integer, 0–100 inclusive. **0 is a documented, legal value** — MoonHalo's `level: 0` while off is not itself a violation of this trait's schema.

- **OnOff trait** — https://developers.home.google.com/cloud-to-cloud/traits/onoff **[DOC]**
  - No required SYNC attributes.
  - QUERY state: `on`, Boolean. MoonHalo's `switch: off` maps to `on: false` — legal.

**What would make Google itself reject/hide a device**: the trait docs describe schema requirements for a service's SYNC/QUERY *responses*, not client-side validation of a third-party hub's driver. Nothing in these four pages describes Google silently hiding a synced device — the "missing from the confirmation screen" behavior described in the symptom is a Hubitat-side, pre-SYNC filtering behavior (§3), not something documented on Google's side. **This is not documented in the sources consulted** — see Open Questions.

Additional context, not a bug report: the community-maintained replacement integration's own documentation (read via GitHub, `mbudnek/google-home-hubitat-community`, a from-scratch reimplementation built specifically because the built-in one had these gaps) states that for a light with colour-temperature support it needs a "Color Temperature Attribute" (default `colorTemperature`), a "Set Color Temperature Command," a default Kelvin range of **2200K–6500K**, a "Color Mode Attribute" to disambiguate RGB vs. CT when both are present, and: *"At least one of 'Full-Spectrum Color Control' and/or 'Color Temperature Control' must be set."* This describes a **different, independently-written integration's** configuration requirements, not Hubitat's built-in app's internal logic — cited here only because it's the closest thing to a documented capability→Google-type mapping found, and because it corroborates that `colorMode` matters when disambiguating CT from RGB, consistent with the bcopeland/Ryan780 exchange above. **[FORUM-adjacent, not Hubitat's own docs.]**

No Hubitat staff post stating an explicit "capability X + capability Y = Google device type Z" mapping table was found for the built-in integration. The bcopeland quote above ("colorMode has to be set... critical for the driver to implement this on any bulb that has both CT and RGB") is the closest thing to an authoritative statement, and it is scoped to dual-mode (CT+RGB) bulbs, not CT-only ones like MoonHalo.

## 4. Most likely causes for the MoonHalo Driver, ranked

MoonHalo's capability set: `Actuator`, `Switch`, `SwitchLevel`, `ColorTemperature`, `ColorMode`, `Light`, `Refresh`, `Initialize`, plus a custom attribute `connectionState` and a custom command `setColorTempStep`. At the time of the symptom: `switch: off`, `level: 0`, `colorTemperature: 3514`, `colorName: Moonlight`, `colorMode: CT`, `connectionState: online` — i.e. every attribute tied to a declared capability already had a non-null value.

1. **`capability "Light"` instead of `capability "Bulb"` [INFERENCE, moderate confidence].** `Light` and `Bulb` are byte-for-byte identical in Hubitat's own capability list (both declare only `switch` ENUM `["on","off"]` and `on()`/`off()` — confirmed by reading `https://docs2.hubitat.com/en/developer/driver/capability-list` directly), yet Hubitat's own official example CT-only driver, `advancedZigbeeCTbulb.groovy` (read in the prior `ct-light-driver-conventions.md` research pass), declares `Bulb`, not `Light` — and Hubitat's Google Home doc itself repeatedly uses the word **"bulbs"**, never "lights," when describing what the integration supports (§1). No forum thread or doc explicitly confirms the integration keys off this capability name, but it is the single cheapest, most plausible, and easiest-to-test divergence between MoonHalo and the pattern every real CT bulb driver in this codebase's prior research actually follows.
2. **Non-standard extra capabilities/attributes for a "plain CT bulb" [INFERENCE, supported by a recurring but unverified community claim].** MoonHalo also declares `Initialize` and `Refresh` (neither appears on any CT/RGBW driver example that was confirmed to work with Google Home in the threads read) and a custom, non-capability `connectionState` enum attribute plus a custom `setColorTempStep` command. The clearest parallel finding is yatse's own conclusion in the Generic-Zigbee-RGBW thread: *"Although Hubitat can use a driver with attributes the device does not actually support - adding that device to Google Home will likely fail?"* — stated as a question by a forum member, not confirmed by staff, but it is the one general principle every solved thread in this table is consistent with (the fix in every *solved* case was narrowing the driver's capability/attribute surface, never widening it).
3. **`colorMode` correctness, by analogy [STAFF-adjacent but scoped to a different case].** bcopeland's staff quote about `colorMode` was specifically about drivers that mix `ColorControl` and `ColorTemperature`. MoonHalo has no `ColorControl` and always sets `colorMode` to `"CT"` (in `installed()` and again at the end of every `applyState()` call in `BenQ_MoonHalo_Bridge_Driver.groovy`), so this specific documented failure mode does not appear to apply — included here only to rule it out explicitly, not as a live suspect.
4. **Google's own device cache, not a driver problem at all [FORUM, low confidence but free to test].** Two independent threads (the "devices won't show up" thread and the general troubleshooting advice in it) point at Google-side caching that a voice "sync my devices" command has fixed for other users, independent of what the driver declares. Cannot be ruled out or confirmed from Hubitat's or Google's docs; worth trying first specifically because it is zero-risk and instant.
5. **`level: 0` while `switch: off` [ruled out].** Google's own `Brightness` trait schema explicitly permits `0` as a valid QUERY value (§2) — this is not a plausible cause on the documented schema, even though it superficially resembles the "unpopulated attribute" failure mode seen in the RGBW/saturation case.

## 5. Concrete steps to try, in order

1. **Say "Hey Google, sync my devices"** (or Google Home app → Settings → re-sync) after the device shows as authorized in Hubitat but before changing anything else. Free, reversible, addresses the Google-side-cache hypothesis (§4.4) first. [FORUM]
2. **Check the hub's Logs at the exact moment of authorization** for the line `"The following devices are not supported by Google Home and will be removed from your device list"` (the exact signature seen in the Generic-Zigbee-RGBW thread). This single log line distinguishes "Hubitat's own pre-filter dropped it" (§3, most of this table) from "Google accepted it but the phone app UI didn't render it" — the two have different fixes, and the docs give no other way to tell them apart.
3. **In the Driver, replace `capability "Light"` with `capability "Bulb"`**, matching `advancedZigbeeCTbulb.groovy`'s pattern and Hubitat's own "bulbs" wording (§4.1). Cheapest structural change; update `metadata { definition { ... } }` in `BenQ_MoonHalo_Bridge_Driver.groovy` (currently line 43), save, then in the Hubitat Google Home app remove and re-add the device before re-authorizing in the Google Home mobile app (removing/re-adding was necessary in more than one thread above after a capability change).
4. **If step 3 doesn't work, temporarily strip MoonHalo down to the minimal trio** Google Home's doc names as supported (`Switch`, `SwitchLevel`, `ColorTemperature`) plus `Actuator`, dropping `Light`/`Bulb`, `ColorMode`, `Refresh`, and `Initialize` for one test cycle, to isolate whether any of the extra capabilities is the actual blocker (§4.2). This is a diagnostic step, not a recommended permanent shape — re-add whichever capabilities prove harmless once the device syncs once.
5. **Re-run `setColorTemperature` and `setLevel` explicitly (with the MoonHalo on) right before re-authorizing**, to eliminate the "attribute technically null/never-sent" failure mode by direct analogy with bertabcd1234's fix advice (§3), even though the symptom's own attribute dump suggests this isn't the issue here — cheap to rule out.
6. **As a fallback if none of the above resolves it**, install the community-maintained Google Home integration (`google-home-hubitat-community`, available via Hubitat Package Manager) instead of the built-in app — several threads recommend it specifically because it gives visibility into and control over the capability→Google-trait mapping that the built-in, closed-source integration does not expose at all.

## 6. Open questions

1. Whether Hubitat's built-in integration's pre-SYNC filter is driven by capability name matching (e.g. specifically `Bulb` vs `Light`), by attribute presence/nullness, by something else entirely, or some combination — **not documented anywhere found**; §4's ranking is inference from precedent, not a confirmed mechanism.
2. Whether the hub log line `"The following devices are not supported by Google Home and will be removed..."` is guaranteed to appear for every silent-drop case, or only some — only evidenced in one forum thread, not documented by Hubitat.
3. Whether Google's own device cache (the "sync my devices" fix) can independently cause a *first-time* authorization to be missing from the "smart devices added" confirmation screen, or whether that fix only applies to devices that *had* synced before and later dropped out — the threads describing it don't distinguish first-time vs. re-sync scenarios.
4. Whether `capability "Initialize"` specifically has ever been documented or reported (by Hubitat staff or the forum) as a cause of Google Home rejecting a device — searched for directly; no thread found either confirming or ruling this out.
5. Whether declaring both `Switch` and `Light`/`Bulb` together (as MoonHalo does, redundantly — both declare the identical `switch` attribute and `on()`/`off()` commands) has any effect, positive or negative, on the built-in integration's type detection — not documented; flagged as an open question in the prior `ct-light-driver-conventions.md` research too (§8.6 there) and still unresolved here.
6. What Hubitat's own SYNC-time colour-temperature range payload (`temperatureMinK`/`temperatureMaxK`, required by Google's `ColorSetting` trait per §2) is actually built from for a driver like MoonHalo's — the Driver only exposes `ctMinKelvin`/`ctMaxKelvin` as *preferences*, not as a capability-visible attribute; whether Hubitat's cloud reads hub-side preference values at all, or only currentValue()-style attributes, when building this SYNC field is not documented anywhere found, and if it silently omits the range, that could independently make ColorSetting SYNC validation fail even though a device's colorTemperature attribute value is populated.
